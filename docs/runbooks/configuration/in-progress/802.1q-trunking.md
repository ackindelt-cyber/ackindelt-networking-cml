# Runbook — 802.1Q Trunking
 
## Overview
 
This runbook provides a structured process for configuring and validating static 802.1Q trunk links on Cisco IOS switches.
 
802.1Q trunking allows a single Layer 2 link to carry traffic for multiple VLANs between network devices while preserving VLAN separation. Trunk links are commonly used between switches and other VLAN-aware infrastructure devices.
 
This runbook focuses on statically configured switch-to-switch trunks using an explicitly defined native VLAN and allowed VLAN list. The example reference design uses two Cisco IOS switches connected by a single 802.1Q trunk carrying multiple VLANs.

## Scope and Assumptions
 
This runbook assumes:
 
- The required VLANs have already been created on each participating switch.
- The physical interfaces used for the trunk have been identified.
- The connected devices support IEEE 802.1Q trunking.
- The native VLAN has been defined for the trunk.
- The allowed VLAN list has been defined for the trunk.
- The trunk interfaces are not currently part of an EtherChannel.
- EtherChannel configuration is handled separately.
- Spanning-tree root placement and other Layer 2 design features are handled separately.
 
This runbook does not cover dynamic trunk negotiation, router-on-a-stick, routed interfaces, EtherChannel trunks, or Layer 3 SVI configuration.

## Reference Design
 
This runbook uses two Cisco IOS switches connected by a single static 802.1Q trunk.
 
The trunk carries VLANs 10, 20, and 30 between the switches. VLAN 99 is used as the native VLAN and is not used for endpoint access.
 
### Devices
 
| Device | Role             | Purpose                           |
|--------|------------------|-----------------------------------|
| SW1    | Cisco IOS switch | First endpoint of the trunk link  |
| SW2    | Cisco IOS switch | Second endpoint of the trunk link |
 
### Trunk Link Summary
 
| Device | Interface | Connected To | Allowed VLANs | Native VLAN |
|--------|-----------|--------------|---------------|-------------|
| SW1    | Gi0/0     | SW2 Gi0/0    | 10,20,30      | 99          |
| SW2    | Gi0/0     | SW1 Gi0/0    | 10,20,30      | 99          |
 
### VLAN Summary
 
| VLAN | Name    | Purpose                |
|------|---------|------------------------|
| 10   | USERS   | User endpoint network  |
| 20   | VOICE   | Voice endpoint network |
| 30   | SERVERS | Server endpoint network|
| 99   | NATIVE  | 802.1Q native VLAN     |
 
**Note:** The values shown in this reference design are examples. Replace interface numbers, VLAN IDs, VLAN names, native VLAN, and allowed VLAN list with those appropriate to the target deployment.

## Prerequisites and Pre-Checks
 
Before configuring the trunk link, confirm that the required VLAN and interface information is available and that the target interfaces can be safely modified.
 
### Prerequisites
 
- [ ] The participating switches are powered on and accessible for configuration.
- [ ] The required device baselines have already been applied.
- [ ] The required VLANs exist on both switches.
- [ ] The trunk interfaces have been identified on both switches.
- [ ] The allowed VLAN list has been defined.
- [ ] The native VLAN has been defined.
- [ ] The target interfaces are not currently used for another production connection.
- [ ] The target interfaces are not members of an EtherChannel.
 
### Baseline Verification
 
Run these commands on both switches before applying the trunk configuration.
 
```bash
show vlan brief
show interfaces status
show interfaces switchport
show etherchannel summary
```
 
### Expected Baseline Results
 
- [ ] The required VLANs exist and are active.
- [ ] The target interfaces are present and available for trunk configuration.
- [ ] The target interfaces are not assigned to an unintended production VLAN.
- [ ] The target interfaces are not currently operating as unintended trunks.
- [ ] The target interfaces are not members of an EtherChannel.
- [ ] No conflicting interface configuration is present on the target trunk ports.

## Configuration Procedure
 
Use this procedure to configure static 802.1Q trunk links between Cisco IOS switches.
 
### Configuration Notes
 
- Configure both ends of the trunk with matching native VLAN and allowed VLAN settings.
- Ensure all VLANs carried by the trunk already exist on the participating switches.
- Replace example interface numbers, VLAN IDs, and VLAN lists with those defined for the target deployment.
- Interfaces previously assigned to a parking VLAN or administratively disabled must be returned to service as part of the trunk configuration.
 
---
 
### Step 1 — Configure Core Trunk Interfaces
 
```bash
enable
configure terminal
 
interface gi0/0 # Targets core trunk interface
switchport trunk encapsulation dot1q # Sets 802.1Q trunk encapsulation
switchport mode trunk # Sets interface to trunk mode
switchport trunk allowed vlan 10,20,30 # Allows VLANs 10,20, and 30 on the trunk
switchport trunk native vlan 99 # Sets native VLAN to 99 on trunk
no shutdown # Administratively enables trunk interface
 
end
write memory
```
 
---
 
### Step 2 — Configure Access Switch Trunk Interfaces
 
```bash
enable
configure terminal
 
interface gi0/0 # Targets access switch trunk interface
switchport trunk encapsulation dot1q # Sets 802.1Q trunk encapsulation
switchport mode trunk # Sets interface to trunk mode
switchport trunk allowed vlan 10,20,30 # Allows VLANs 10,20, and 30 on the trunk
switchport trunk native vlan 99 # Sets native VLAN to 99 on trunk
no shutdown # Administratively enables trunk interface
 
end
write memory
```

## Post-Configuration Validation
 
Use this section to confirm that the 802.1Q trunk is configured correctly and operating in the expected state after implementation.
 
### Step 1 — Verify Trunk Operational State
 
Run on both switches.
 
```bash
show interfaces trunk
```
 
Expected results:
 
- [ ] The configured trunk interface appears in the trunk summary.
- [ ] The interface is operating in trunking mode.
- [ ] 802.1Q is shown as the trunk encapsulation.
- [ ] The native VLAN is VLAN 99.
- [ ] VLANs 10, 20, and 30 are allowed on the trunk.
- [ ] The expected VLANs are active and forwarding across the trunk.
 
---
 
### Step 2 — Verify Detailed Trunk Interface State
 
Run on both switches.
 
```bash
show interfaces Gi0/0 switchport
```
 
Expected results:
 
- [ ] Administrative mode is configured for trunking.
- [ ] Operational mode is trunking.
- [ ] Trunk encapsulation is 802.1Q.
- [ ] The configured native VLAN is VLAN 99.
- [ ] The trunk allowed VLAN list contains VLANs 10, 20, and 30.
- [ ] No unexpected access-port configuration is affecting the interface.
 
---
 
### Step 3 — Verify Interface Status
 
Run on both switches.
 
```bash
show interfaces status
```
 
Expected results:
 
- [ ] The trunk interface is administratively enabled.
- [ ] The trunk interface is physically connected.
- [ ] The interface is identified as a trunk rather than an access VLAN.
- [ ] No unexpected interface state is present on either side of the trunk.

---

## If Validation Fails
 
If post-configuration validation does not produce the expected results:
 
- Identify which validation step failed.
- Review the trunk configuration on both ends of the link for missing, incorrect, or conflicting settings.
- Confirm that the native VLAN and allowed VLAN list match on both sides.
- Confirm that the required VLANs exist on both switches.
- Correct the affected configuration.
- Re-run the failed validation step.
- If the issue cannot be resolved, return the affected interfaces to their previous known-good state before continuing.

---

## Backout Considerations
 
Changing or removing trunk configuration can interrupt Layer 2 connectivity for VLANs carried across the affected link.
 
Before removing or changing the configuration, confirm:
 
- The original trunk configuration is documented.
- The previous interface mode and VLAN configuration are known.
- The affected allowed VLANs and native VLAN are documented.
- Any services or downstream devices dependent on the trunk are understood.
- Both ends of the trunk can be returned to their previous known-good configuration if required.
 
For lab use, restore the last known working configuration before continuing additional validation.
